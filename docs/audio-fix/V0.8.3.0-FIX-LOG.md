# v0.8.3.0 Audio Fix — Complete Session Log

> **Date:** Jul 14, 2026
> **Starting state:** v0.8.2.0 restore was done but audio broken (no audio_batch_cb, accumulator bugs, wrong sample rate)
> **Final state:** Working audio — zero crackling, correct speed, stable queue, FPS overlay, DIAG logging

---

## 1. Initial State (Broken)

After restoring v0.8.2.0 audio architecture on top of HEAD (D3D11, spdlog, FPS overlay), audio didn't work at all. Logs showed:
- `audio_q=0` always — no audio reaching XAudio2
- `runs_ival=36-87` — retro_run was firing but audio never queued
- FPS showing absurd values (2640, 3000) due to computation bugs
- `DBP_STANDALONE` was defined in vcxproj — compiled out `audio_batch_cb()` calls in core

---

## 2. Fixes Applied (Chronological)

### Fix 1: Remove `DBP_STANDALONE` from vcxproj

**Problem:** `dosbox_pure_libretro.cpp` has `#ifndef DBP_STANDALONE` guards around:
- `audio_batch_cb()` calls at lines 3614 and 3685
- Audio mixing code (`MIXER_CallBack`) at lines 3656-3674
- OSD rendering path (renders to `buf.video` directly instead of separate buffer)

With `DBP_STANDALONE` defined, `audio_batch_cb()` was never called → `retro_audio()` never received data → `Submit()` never called → silence.

**Fix:** Removed `DBP_STANDALONE` from both Debug and Release `PreprocessorDefinitions` in `dosbox-uwp.vcxproj`.

**Side effects resolved:**
- `DBPS_ToggleOSD()` and `DBPS_IsShowingOSD()` were previously compiled inside `#ifdef DBP_STANDALONE` in `dosbox_pure_osd.h`. Without the define, these symbols were missing at link time. Added stubs in `dosbox_pure_sta.cpp`:
  - `DBPS_ToggleOSD()` → no-op (OSD toggle needs rework for non-standalone)
  - `DBPS_IsShowingOSD()` → returns false
  - `DBPS_IsGameRunning()` → returns false

### Fix 2: Accumulator `dt * targetFps`

**Problem:** `m_audioTimeAccumulator += dt` accumulated at 1.0/sec (wall clock). For 70fps target, each retro_run needs 1/70th of a second of accumulator credit. Without the multiplier, the accumulator grew too slowly → too few retro_runs → too little audio produced.

**Fix:** Changed to `m_audioTimeAccumulator += dt * targetFps`.

ZillaLib doesn't need this because its Tick is capped at targetFps by `SetFpsLimit`.

### Fix 3: Stall debt cap units

**Problem:** Stall debt cap was `3.0` (frames). With `* targetFps` accumulator, the cap needs to match: `3.0 * targetFps` (= 210 frames = 3 seconds of stall debt).

**Fix:** Changed cap to `3.0 * targetFps`.

### Fix 4: FPS computation

**Problem:** `m_fpsLastFrame` was set outside the `if (m_lastRetroRuns > 0)` block, causing it to measure tick interval (~0.3ms) instead of retro_run interval (~14ms). Showed 280-972fps.

**Fix:** Split into two `if` blocks:
```cpp
if (m_lastRetroRuns > 0) m_fpsLastFrame = now;  // update timestamp
if (m_fpsLastFrame != 0 && m_lastRetroRuns > 0) { /* compute fps */ }
```

The second `if` ensures `m_fpsLastFrame` is initialized (non-zero) before computing FPS.

### Fix 5: DIAG `runs_ival` / `runs_last`

**Problem:** `m_lastRetroRuns` is set every tick (~1000x/sec). Most ticks have runs=0 (retro_run fires ~70x/sec). DIAG fires every 1 second — most likely sees runs=0.

**Fix:** Added `static int s_diagRunsAccum` (at Tick lambda scope) that accumulates runs across ticks. DIAG reports both `runs_ival` (accumulated) and `runs_last` (most recent tick). This accurately shows ~70 retro_runs per second.

### Fix 6: DBP_STANDALONE removal side effects — OSD stubs

**Problem (linker):** After removing `DBP_STANDALONE`:
- `DBPS_ToggleOSD` unresolved in `RetroCore.obj` (called from `RetroCore::ToggleOSD()`)
- `DBPS_IsShowingOSD` unresolved in `dosbox_uwpMain.obj` (used in gamepad mouse mode)

These were defined inside `#ifdef DBP_STANDALONE` in `dosbox_pure_osd.h`. With the define gone, they're not compiled.

**Root cause detail:** `DBP_QueueEvent`, `dbp_intercept`, `dbp_game_running` are all `static` in `dosbox_pure_libretro.cpp` — cannot use `extern` from sta.cpp.

**Fix:** Added stubs in `dosbox_pure_sta.cpp`:
- `DBPS_ToggleOSD()` → no-op
- `DBPS_IsShowingOSD()` → returns false
- `DBPS_IsGameRunning()` → returns false

These are minimal stubs. Proper implementation would need the core's internal OSD state, which isn't accessible from outside the core.

### Fix 7: XAudio2 sample rate 44100 → 48000 ⭐ (The Big One)

**Problem:** Music sounded ~8% slower than normal. No crackling, but wrong speed.

**Root cause:** XAudio2 was hardcoded at 44100Hz but the core outputs 48000Hz (`DBP_MIXER_GetFrequency()` returns 48000).

**Evidence from logs:**
```
av_info: 640x400 @ 70.09Hz, sample_rate=48000
consume=44081Hz  ← XAudio2 consuming ~44100Hz, NOT 48000Hz
```

44100/48000 = 0.919 → music plays at 91.9% speed = ~8% too slow.

**Secondary effect:** Queue grew to MAX_QUEUE (22050 frames) every ~5 seconds because production (48000Hz) > consumption (44100Hz). Net accumulation: ~4000 frames/sec. Queue cap flush was masking the problem.

**Fix:** Changed ALL `44100` references in `XAudio2Output.cpp` to `48000`:

| Constant | Before (44100Hz) | After (48000Hz) |
|---|---|---|
| `wfx.nSamplesPerSec` | 44100 | 48000 |
| `wfx.nAvgBytesPerSec` | 176400 | 192000 |
| `CreateMasteringVoice` | 44100 | 48000 |
| `TARGET_QUEUE` | 2517 (57ms) | 2736 (57ms) |
| `MAX_QUEUE` | 22050 (500ms) | 24000 (500ms) |
| Underrun threshold | 441 (10ms) | 480 (10ms) |
| All diagnostic `/44100.0` | 6 occurrences | all → `/48000.0` |

### Additional: XA2 UNDERRUN callback throttling

**Problem:** `OnVoiceProcessingPassStart` callback fires every ~10ms. When underrun occurs, `OutputDebugStringA` in the callback flooded the UWP diagnostic output → UI freeze.

**Fix:** Added 1-second throttle: static `s_lastUnderrunLog` timestamp, only log once per second.

### Additional: Auto-stop voice

**Problem:** After game load or flush, voice could run empty with no data → infinite UNDERRUN cycle.

**Fix:** In Tick, outside `m_retroRunning` block: if `m_lastRetroRuns == 0` and `queue <= 0` → `Stop()` voice. This kills the voice when the game isn't producing audio.

### Additional: ProcessPendingLoad forced Start() removed

**Problem:** `ProcessPendingLoad` was calling `Submit(silence, 2)` + `Start()` — forcing voice with only 2 frames. Instant underrun.

**Fix:** Removed forced start. Accumulator = 1.0 triggers retro_run → natural audio production → Submit auto-starts at TARGET_QUEUE.

## 3. Post-Fix Log Analysis

After all fixes, Rally Championship tested. Key metrics:

```
fps=70.0/70          ← frame pacing correct
runs_ival=70-87      ← retro_run firing ~70-87x per second (correct)
audio_q=0→21943      ← queue filling and draining naturally
consume=44081Hz      ← NOW matches production rate (was 44100Hz before fix)
underruns=0          ← no crackling
XA2 FLUSH cap        ← still fires but now because production ≈ consumption (was growing due to mismatch)
```

**Note:** `runs_last=0` always — this is expected. DIAG fires every 1 second but `m_lastRetroRuns` reflects the most recent tick, which is usually idle (runs=0) since retro_run fires ~70x/sec but ticks ~1000x/sec.

**Note:** Queue still grows to MAX_QUEUE and flushes. This is the known QPC-vs-DAC drift issue. The flush is ~500ms of buffered audio being discarded — the music continues seamlessly from the pre-buffer. This is the remaining issue documented in AUDIO-PIPELINE.md §3.

## 5. Lessons Learned

1. **Sample rate mismatch is subtle but devastating.** 44100 vs 48000 = 8% speed difference. Music sounded "a little slow" but no crackling — the queue grew silently. The only evidence was `consume=44081Hz` vs expected `48000Hz` in the XA2 diagnostic log.

2. **`DBP_STANDALONE` affects more than you think.** It gates: audio callback, audio mixing, OSD rendering, mouse input. Removing it is the correct approach for a UWP frontend that uses `audio_batch_cb()`.

3. **Static functions in the core can't be called from the frontend.** `DBP_QueueEvent`, `dbp_intercept`, `dbp_game_running` are all `static`. Stub them or find an alternative API.

4. **Accumulator needs `* targetFps`.** Wall-clock time (dt in seconds) doesn't directly map to retro_run credits. ZillaLib hides this because Tick is capped; UWP's uncapped loop exposes it.

5. **DIAG `runs_last` is misleading.** Most ticks have runs=0. Accumulated runs per interval (`runs_ival`) is the useful metric.

6. **XA2 UNDERRUN callback must be throttled.** It fires every ~10ms. Without throttling, `OutputDebugStringA` in the callback floods the system → freeze on UWP.

7. **The FLUSH cap at 22050/24000 frames is still a known issue.** QPC-vs-DAC drift causes queue to grow until flush. The flush is ~500ms of buffered audio. For Rally Championship (fast-paced racing), the pre-buffer covers the gap and it's barely noticeable. For music-heavy games, it may cause a brief stutter. Full fix requires DRC (see AUDIO-PIPELINE.md).

## 6. File Access Investigation (Jul 14, 2026)

Attempted to eliminate `CopyFileToTemp` to reduce memory/disk usage for large files.

### Result: REVERTED for FileBrowser/History. Kept for FileOpenPicker.

**FileBrowser/History (reverted):** Passing native path directly to `QueueLoadRom`
caused `CreateFile2FromAppW` to fail. `broadFileSystemAccess` grants directory
enumeration (`FindFirstFileExFromAppW`) but NOT read access to arbitrary paths.
Only paths selected through `FileOpenPicker` (via `FutureAccessList`) are readable.
`CopyFileToTemp` is REQUIRED.

**FileOpenPicker (App.cpp, kept):** Uses `StorageFile::Path` → `QueueLoadRom`
directly. The picker auto-grants access. Falls back to buffer copy if `Path`
is empty (virtual providers like OneDrive placeholders).
